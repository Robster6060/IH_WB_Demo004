# Terrain Stamp: Blender 5.0.1 → UE5.8 Static Mesh Pipeline

Canonical process for building Invisible Hand Terrain Stamp static-mesh assets. First built for `TableMesa001`; reuse for every future stamp by re-running stage 1-3 with new parameters, then repeating stages 4-10 unchanged.

Companion script: `../TS_Vertical/Domes/TableMesa001/TableMesa001_generate.py` (stages 1-3, Blender-side).

No automation tool drives Blender or UE5.8 directly in these sessions - stages 1-3 are a script you run in Blender's Scripting tab; stages 4-10 are manual UE5.8/Blender UI steps captured here as a checklist.

**Live location:** this entire tree lives under `IH_WB_Demo004`'s own Content folder (`D:\Projects\ClaudeProjects\IH_WB_Demo004\Content\InvisibleHand\World\TerrainStamps\`), confirmed 2026-09-08 as the current live UE5.8 project. `D:\InvisibleHand\` (a different drive location entirely) is cold storage/archive per its own README - not a live project, no `.uproject` file - do not build or import assets there.

## Category taxonomy and folder map

- `TS_Vertical/` (PLUS/raised landforms)
  - `Domes/` - Butte, Volcano, Table Mesa
  - `Ridges/` - mountain range ridge systems
  - `Cliffs/` - escarpment/cliff-face stamps
- `TS_Inverted/` (MINUS/cut landforms)
  - `Bowls/` - lake basins, cave mouths
  - `Canyons/` - single canyons and composite canyon systems (`RadialConvergentTrough`/`Stamp_Canyon`)
  - `Scoops/` - harbor scoops, fjords

Each stamp gets its own numbered subfolder (`TableMesa001/`, `Butte001/`) holding its `.blend`, generator script, and (once exported) its FBX - the UE5.8 `.uasset` lives in the matching Content-browser path once imported.

## Stage 1-3: Blender (see the per-stamp `_generate.py` script)

Scene unit setup (metric, 1 Blender Unit = 1cm to match UE5's cm-scale units), parametric ring-stack base geometry (mirrors `AIH_TerrainStampActor`'s Bottom/Top/intermediate-ring model), footprint irregularity + cap undulation, UV0 unwrap. Re-run the script after editing its parameter block to iterate.

## Stage 4: Export FBX from Blender

1. Select only the stamp object (and nothing else) in the viewport.
2. `File > Export > FBX (.fbx)`.
3. In the export panel:
   - **Include > Limit to > Selected Objects**: on.
   - **Transform > Forward**: `-Y Forward`; **Up**: `Z Up` (Blender's native "Unreal Engine" axis pairing - no extra rotation needed since this pipeline is Blender-native, not SketchUp-sourced).
   - **Transform > Apply Scalings**: `FBX All`.
   - **Transform > Apply Unit**: checked.
   - **Geometry > Smoothing**: `Face`.
   - **Geometry > Tangent Space**: checked (needed if a normal map is added later).
4. Save the export settings as an Operator Preset (the `+` next to the preset dropdown) named `IH_TerrainStamp` so future stamps are one click.
5. Export to the stamp's own folder as `<StampName>.fbx` (e.g. `TableMesa001.fbx`).

## Stage 5: RETIRED - Mesh Terrain is not usable for this pipeline

**Resolved 2026-09-08, from Epic's own documentation (no empirical test needed):** UE5.8's "Crafting Mesh Terrain" documentation explicitly states its `Convert Mesh` tool only goes one direction - a Static Mesh **into** a Mesh Partition - with no documented export/bake/convert-back path to a standalone, portable `StaticMesh` asset. A sculpted Mesh Terrain result stays permanently bound to its World Partition level. It also hard-requires an Open World (World Partition) level to exist at all ("You must use Mesh Partition in a World Partition level").

**Verdict: do not use Mesh Terrain for Terrain Stamps.** It's built for terrain that lives permanently in one place, not for a catalog of placeable landform props. Skip straight from Stage 4 (Blender FBX export) to Stage 6 (Nanite + collision) using the Blender-exported mesh directly.

**Fallback for weathering/erosion detail** (per this stage's original contingency): do any additional cliff-face/strata detail pass back in Blender (extending stage 3's Displace-modifier approach, or a manual sculpt pass) rather than in UE5.8. Not required for `TableMesa001` at its confirmed mid-detail/set-dressing fidelity target - only revisit if a future stamp needs a hero-asset-level weathering pass.

## Prerequisite (one-time, project-wide): Shader Model 6

Nanite requires SM6. If UE5.8 shows "Missing Project Settings! Shader Model 6 (SM6) is required to use Nanite assets" - go to **Project Settings > Platforms > Windows > D3D12 Targeted Shader Formats**, check **SM6** (leave existing formats like SM5 checked too), then restart the editor and let it finish its one-time shader recompile. Confirmed needed on `IH_WB_Demo004` 2026-09-08; already done, future stamps shouldn't hit this again.

## Stage 6: Nanite + native collision

On the Static Mesh asset that will actually ship (post Stage 5, whichever path it took):

1. Static Mesh Editor > **Nanite Settings > Enable Nanite**: on.
2. Leave **Fallback Mesh** generation at its default (`Auto`) initially; if collision feels too heavy or too coarse in Stage 10 testing, tune **Keep Percent Triangles** / **Fallback Relative Error** here rather than building a separate hand-made collision proxy.
3. **Collision Complexity**: `Use Complex Collision as Simple` - this resolves against the Nanite Fallback Mesh, not the full-density render mesh, giving accurate cliff-silhouette collision at a fraction of full-mesh cost.
4. Assign a physical material (e.g. `PhysicalMaterial_Rock`) appropriate to a stone/rock landform.

## Stage 7: Import/placement settings

1. Import FBX with **Import Uniform Scale**: `1.0` (no correction needed given the stage-1 unit convention).
2. **Generate Lightmap UVs**: off by default - confirm `IH_WB_Demo004` is fully Lumen dynamic-GI first (flagged open item); turn on only if the project still bakes static lighting anywhere this mesh will appear.
3. Place the resulting `.uasset` under the matching Content-browser path, e.g. `TS_Vertical/Domes/TableMesa001/`.

## Stage 8: Material assignment - DONE, simpler than originally planned

**Resolved 2026-09-09.** The original plan (a bespoke material sampling Absolute World Position Z + slope to reimplement the `DT_ASLSlopeBiome.csv` hex-band table) was replaced after inspecting `MTL_MWAM_AutoMaterial_MASTER`'s actual graph: the right move is simply to use **the same auto-material already texturing the rest of the world's terrain**, for visual consistency, not a separate reimplementation.

Graph inspection found: five procedural layers (Rock/Stones/Grass/Dirt/Snow, matching the project's existing `PM_MW_*` physical materials), each a self-contained texture-sample unit feeding a shared `MF_MWAM_DefaultLayer` function (ordinary UV/texture logic, nothing Landscape-exclusive) into a standard `MakeMaterialAttributes` node. Three genuinely Landscape-exclusive special outputs exist off to the side (`LandscapeVisMask`, a footstep `Physical Material Output`, and a `Landscape Grass Output` for native foliage) - none of them feed the core color/normal chain, so they simply go inert on a StaticMesh rather than breaking anything.

**Steps that worked:** right-click `MTL_MWAM_AutoMaterial_MASTER` -> Create Material Instance -> named `MI_TerrainStamp_TableMesa001` -> moved into the stamp's own folder -> assigned to Element 0 in the Static Mesh Editor's Material Slots -> saved. Confirmed rendering with no shader compile errors once the viewport was correctly framed on the (very large) mesh - the material currently shows uniform placeholder "COL" texture tiling since all five layers share one temp texture project-wide (`TEX_MW_Temp_col`), not a bug in this pipeline; real per-layer texture variation will appear automatically once the base project's texture art is finalized.

**Repeat for every future stamp:** same Create-Material-Instance-and-assign steps, one instance per stamp (or reuse one shared instance across stamps if no per-stamp tinting is ever needed - not decided yet, default to one-per-stamp for now).

**Correction, 2026-09-10 - the "matches the rest of the world's terrain" assumption above was wrong.** Reading `AIH_WB_IslandActor::ApplyDtBiomeColorBands` (`IH_WB_IslandActor.cpp`, its own header comment cites `IH-DEC-052 revised Phase 2`) found that the REAL live island terrain's actual coloring is **not** `MTL_MWAM_AutoMaterial_MASTER`'s texture layers at all - it's a flat, hard-banded per-`DT_ASLSlopeBiome`-row color, and that function's own comment states it "replaces the old texture smoothstep system entirely (decided: full replace, not kept as a fallback)." So `MI_TerrainStamp_TableMesa001` was texturing the stamp to match a system the rest of the world's terrain doesn't actually use anymore.

**Fixed via `Scripts/build_asl_band_material.py`** (run once, reusable for every future stamp): rather than reproducing the island's own per-triangle `UProceduralMeshComponent`-sectioning approach (which would forfeit Nanite and this pipeline's own Stage 6 collision setup), a small **World-Z lookup material** was built instead:
- **`T_ASLBandLUT`** - a 256x1 texture, Nearest-filtered, Clamp-addressed, no compression/mip blur, baked directly from `DT_ASLSlopeBiome` (not hand-transcribed thresholds) by sampling the real classifier's ASL-range logic at 256 evenly-spaced elevation values from -25m to 2400m.
- **Verified simplification, not an approximation:** every row's `biomeColor` is identical across all 7 slope subdivisions within a given elevation tier in the current `DT_ASLSlopeBiome` data - slope does not actually affect color today, only elevation does. A pure World-Z lookup therefore reproduces the exact same visual result the real per-triangle classifier would (which also checks slope), for the data as it stands now. If a future `DT_ASLSlopeBiome` revision ever gives two rows in the same elevation tier different colors by slope, this LUT would need a second (slope) axis added - re-run the bake script after checking that assumption still holds.
- **`M_TerrainStampASLBand`** - samples `AbsoluteWorldPosition.z`, converts cm to meters, normalizes into the LUT's [-25, 2400] range, and point-samples `T_ASLBandLUT` for `BaseColor` (Roughness fixed at 0.85).
- **`MI_TerrainStamp_TableMesa001_ASLBand`** (in the stamp's own folder) - a plain instance of the material above, now assigned to `TableMesa001` slot 0, replacing the old `MI_TerrainStamp_TableMesa001` (kept on disk, unused, in case a texture-based look is wanted again later).
- Also completed Stage 6 step 4 while verifying this (`Scripts/verify_tablemesa001_nanite_and_collision.py` first surfaced it): `phys_material` had never actually been assigned despite this doc's own checklist - now set to `PM_MW_Rocks` (the project's existing rock-terrain physical material).
- Not yet visually confirmed in PIE - the LUT/material graph compiles clean and the baked colors were verified against the real `DT_ASLSlopeBiome` data directly, but no screenshot comparison against a real placed island has been taken yet.

## Stage 9: PCG ground cover hookup

**Revised 2026-09-09 after inspecting `MTL_MWAM_AutoMaterial_MASTER`'s actual graph:** the main terrain's ground cover may not be PCG at all - the master material has a `GrassTypes` section feeding a native **Landscape Grass Output** node (driven by the same RocksMask/StonesMask/GrassMask/DirtMask/SnowMask layer masks used for coloring). Landscape Grass Output is a Landscape-exclusive special output - it will NOT function on a StaticMesh, the same way the material's other two Landscape-only outputs (`LandscapeVisMask`, the footstep `Physical Material Output`) won't. **Before building anything for this stage, confirm in-editor which mechanism the rest of `IH_WB_Demo004`'s terrain actually uses for ground cover** - open the Landscape actor's Grass Type assignments (Landscape Details panel) and separately check whether a PCG Graph asset also exists targeting `OWD_Plants_Pack`/`Rock_Collection_04`/`Ultimate_Rocks`. If it's genuinely Landscape Grass Output (not PCG), `TableMesa001` will need its own independent PCG graph built from scratch (reusing the same five procedural masks' *logic*, reimplemented in PCG - e.g. a PCG graph sampling the mesh's own slope/height and picking OWD_Plants_Pack/Rock_Collection_04 meshes accordingly) rather than being added as a source to an existing graph, since a StaticMesh can't hook into Landscape Grass Output at all.

## Stage 10 finding (2026-09-09): confirmed the IslandMesh/WWF-only placement constraint gap is real and blocks Ship/Mannequin-specific tools, NOT general collision

Live-tested in `L_TerrainStamp_Test` PIE: **Grand Theater structures (`IH_StructurePlacementActor`) and Town Grids placed correctly on `TableMesa001`** - confirms the mesh's own collision (Nanite Fallback + Complex-as-Simple) works fine for standard placement/line-trace queries. However, **Place Ship sailed straight through the mesh with no collision**, and the **Mannequin click-to-place tool placed 6 Mannequins at wildly wrong locations** (observed ~1377m/9400m away from the stamp's actual position, plausibly landing on a real generated island elsewhere in the 105.7x65km Realm instead) - both symptoms consistent with the ray/query simply passing through `TableMesa001` rather than recognizing it. Root cause, per existing canon (not a new bug): the approved-but-unbuilt **"IslandMesh/WWF-only placement constraint"** - Place Ship and the Mannequin tool are built to recognize the canonical `IslandMesh`/`ShelfMesh` actor classes specifically, not a generic `StaticMeshActor`. `TableMesa001` isn't registered with that system. This is real Demo004-integration-time work, not something to fix in this pipeline - noted here so it isn't re-discovered as a mystery bug later. **Practical implication for Stage 10's own collision-walk-test:** the DEV Mannequin tool can't be used to test walking on a Stamp until this integration exists; a manual test (placing a real Character Blueprint/Player Start near the stamp instead of relying on the click-to-place tool) is the fallback if a walk-test is needed before that integration work happens.

## Stage 12b (2026-09-11, shipped): bounding-box scale grips

Two references were found and used instead of designing from scratch: the old `IH_WB_Stamps001` lab project's own full corner/edge/face grip system (proves the pin-opposite-face math and the color scheme, but is built around live spline/ring data this static-mesh actor doesn't have, and its translucent gizmo material lives in that project's own content); and `AIH_TownGridManager` (THIS project) - an already-shipped, simpler grip-resize system for Town Grid footprints, whose hit-test/drag-state-machine shape (`TryHitGripAtWorld`/`Begin/Update/EndGripDrag`) is what this round actually mirrors, since it's already proven in this exact input pipeline.

- **9 grips**: `EIHStampGripHandle` (`IH_TerrainStampActor.h`) - `PosX`/`NegX`/`PosY`/`NegY` (face grips), `Top` (Z/height), and 4 XY corners. `IHStampGripHandleToSignedAxisMask` maps each to which local axes it affects and in which signed direction, driving one generic masked-delta application in `UpdateGripDrag` instead of a per-handle switch.
- **Visuals**: `AIH_TerrainStampActor` gained `BoundingBoxMesh` (a translucent `/Engine/BasicShapes/Cube`, new `M_TerrainStampGizmoTranslucent` material built via `Scripts/build_stamp_gizmo_material.py`) and 9 `GripMarkers` (`/Engine/BasicShapes/Sphere`, tinted `IHTerrainStampColors::BoundingBoxGripColor #31D492` via the existing `CreateStampTintMaterial` helper). Both are children of `SceneRoot`, not `MeshComponent` - their own on-screen size stays constant regardless of the stamp's current scale, sidestepping the lab project's whole counter-scale-by-geometric-mean scheme (which only existed because its grips WERE children of its scaled mesh). Shown/hidden together with the selection tint (`SetStampSelected` -> `UpdateBoundingBoxGizmoVisibility`).
- **Hit-testing, corrected from an initial design mistake**: a first pass hit-tested grips against a terrain-surface raycast/3D-distance check, mirroring Town Grid's `TryHitGripAtWorld` literally - caught before shipping that this doesn't work for a genuinely 3D box: a corner grip on a tapered/dome-shaped stamp sits over EMPTY SPACE past the mesh's actual silhouette (the bounding box corner extends beyond a rounded mesh's surface), so a raycast there either misses entirely or hits ground far below, way outside any reasonable 3D pick radius. Fixed by hit-testing in SCREEN SPACE instead: `UIH_BuildPaletteSubsystem::TryFindTerrainStampGripAtScreen` projects each of the stamp's 9 cached grip world positions (`AIH_TerrainStampActor::GetGripMarkerWorldPositions/Handles`, refreshed every `RegenerateBoundingBoxGizmo()` call) via `APlayerController::ProjectWorldLocationToScreen` and picks the nearest within a pixel radius - works regardless of what (if anything) is directly behind the grip in world space.
- **X/Y/corner drag, also corrected for the same reason**: a per-tick world point can't come from a terrain raycast either (same empty-space problem while actively dragging a corner outward). Instead, `BeginStampGripDrag` captures a camera-facing drag plane (`GripDragPlaneOrigin` = the grabbed grip's own world position, `GripDragPlaneNormal` = camera forward, both fixed for the whole drag) and `UpdateStampGripDrag` intersects the cursor's deprojected ray against it every tick - the lab project's own original drag-plane technique, which this round almost skipped in favor of Town Grid's simpler ground-point approach before realizing Town Grid's approach only works because ITS grips sit on a flat, always-hit-able footprint. The resulting world point is transformed into the actor's local space via `InverseTransformVector` (not two positions inverse-transformed and subtracted - stays correct even after the pin-compensation below has already shifted the actor's own location mid-drag), then re-derives a fresh scale from `DragStartMeshScale3D`/`DragStartLocalExtent` each tick (never compounds - dragging back to the start point exactly restores the original extent).
- **Z (Top) drag - the one axis neither reference could drive from a world point** (a horizontal terrain raycast can't carry a vertical delta): reuses this project's own already-proven vertical-drag technique - `IH_Cube2FlyPlayerController`'s free-mouse camera pan drives movement directly from raw per-tick screen-space mouse Y delta (`MouseDragDelta.Y * PanCmPerMousePixel`). Top does the same (`ScreenMouseDeltaYForZ * TerrainStampHeightDragCmPerPixel`, 150cm/px), folded onto the CURRENT extent each tick rather than a fixed drag-start baseline (an accepted, deliberately simpler trade-off - the X/Y "total from start" model needs a screen-pixel-to-world-distance mapping to build an equivalent baseline, which Top has no natural analogue for).
- **One-sided pin vs. Ctrl-symmetric**: `bGripDragSymmetric` is captured once at grab time (not re-polled mid-drag) from the Ctrl key state. Non-symmetric (default): `DragPinLocalPoint`/`DragPinWorldPosition`, captured once in `BeginGripDrag`, are re-transformed by the actor's LIVE transform every tick and compared to the fixed drag-start world position - the exact difference is the location shift that holds the opposite face/corner fixed in world space (the lab project's own technique, generalized here to all 9 handles including Top, where growing height keeps the BASE planted rather than the top). Symmetric: no location shift - the stamp grows about its own pivot. Matches the user's own spec: X/Y/corner support both; Top is always one-sided (growing a landform's height downward would sink it into the terrain).
- **Scale clamp**: `[MinStampScaleFactor, MaxStampScaleFactor]` = `[0.4, 3.0]` per axis (tunable constants, `IH_TerrainStampActor.h`) - not a user-specified number, a starting default.
- **Undo**: reuses `FIHStampUndoRecord`/`PushStampUndoRecord`/`StampUndoStack` completely unchanged - a grip-drag is just another `Transform`-type record (scale is already part of `FTransform`), pushed by the new `EndStampGripDrag` exactly like `EndStampMoveDrag` (only if the transform actually changed). `EndStampGripDrag` also calls `ApplySelectedTerrainStampTransform()` to reapply the height grid, matching Rotate's existing precedent of not re-running the depth-constrained surface placement on a post-place transform change.
- **Input wiring**: `IH_Cube2FlyPlayerController` checks a grip hit BEFORE the Shift+move-drag block (no Shift required - grips are their own widget layer, mirroring Town Grid's own grip-before-move ordering), reading Ctrl at grab time; new `bStampGripPointerCapture` mirrors `bStampMovePointerCapture` end to end (mouse-down begins, per-tick mouse-move updates, mouse-up ends).
- **`IH_WB_Demo004Editor` builds clean.** Verified via a headless spawn (`Scripts/diagnose_stamp_grip_setup.py`): the gizmo material now resolves with no CDO-constructor error (it didn't exist yet on the FIRST run, before `build_stamp_gizmo_material.py` created it - confirmed the graceful "if Succeeded()" fallback worked as intended in the meantime), all 9 grip markers get real meshes/materials and start hidden. The actual drag gestures themselves are plain C++ (not UFUNCTION-exposed) and need the user's own PIE pass.

### Stage 12b addendum (2026-09-11): grip size/layout fix after first PIE pass

First real PIE screenshot showed the translucent box correctly, but all 9 grips were invisible. Root cause: `GripMarkerWorldSizeCm` was a fixed 400cm (4m) sphere - against `TableMesa001`'s ~1400m footprint that's under 0.3% of the object's width, imperceptible at any normal viewing distance (the box itself is only visible because it's SIZED to match the mesh's own extent; the grips weren't). Fixed by computing grip size dynamically in `RegenerateBoundingBoxGizmo` - 12% of the average local extent, clamped to `[500cm, 6000cm]` - so a grip is always a sane fraction of whatever stamp it's attached to, small stamp or large.

Also incorporated a layout note from the user: no grips on the bottom plane - only the 4 side-middles (`PosX`/`NegX`/`PosY`/`NegY`, already correct), the 4 XY corners repositioned to the TOP of the box (previously sat at vertical center, since a corner's `SignedAxisMask` never touches Z for scaling purposes - now the visual position overrides to the top face specifically for corners, independent of the scale mask), and the single top-center `Top` grip. Purely a visual repositioning - the drag math is unaffected since corner scaling never reads Z either way.

### Stage 12c (2026-09-11, shipped): adjustable sink depth ("merge into IslandMesh")

New canon requirement, confirmed by the user after two rounds of clarification: the 9 bounding-box grips are ONLY for extension/contraction of the mesh - sink depth is controlled through Shift+Drag itself, which becomes a true X/Y/Z move (unlike IslandMesh relocation, which is X/Y only) rather than X/Y with Z fully auto-derived from the fixed depth constraint.

- **`AIH_TerrainStampActor::DepthBelowSurfaceCm` split into two**: `DefaultDepthBelowSurfaceCm` (the original fixed 100cm floor - a stamp can never rise shallower than this, which would create a gap) and a new instance field `CurrentDepthBelowSurfaceCm` (starts at the default, persists as real per-actor state like `StampRotationDeg`, adjustable deeper via `SetManualSinkDepthFromDragTotal` - see the addendum below for why this isn't a simple per-tick accumulator).
- **Shift+Drag now drives depth too**: `UIH_BuildPaletteSubsystem::UpdateStampMoveDrag` gained a vertical-distance parameter - sets sink depth (mouse moved down = sink deeper) BEFORE `ApplyWorldSurfacePlacement` each tick, so X/Y repositioning (from the terrain-surface raycast) and Z sink depth (from vertical mouse movement) are two independent input channels within the same single gesture, never fighting each other.
- **Absolute "never fully invisible" safety backstop**: previously the backstop that stops the stamp's highest point from sinking below `SurfacePoint.Z - DepthBelowSurfaceCm` would have sunk right along with an adjustable depth, stopping being a real safety net. Replaced with a new `MinVisibleTopMarginCm` (50cm) measured from the CURRENT surface, independent of however deep `CurrentDepthBelowSurfaceCm` has grown - past a certain drag distance the stamp simply stops sinking further, rather than ever fully disappearing.
- **Bug caught and fixed while touching this code**: `ApplyWorldSurfacePlacement`'s bottom/top local-Z math was reading raw UNSCALED mesh asset bounds, ignoring `MeshComponent->GetRelativeScale3D()` entirely - harmless before Stage 12b (no way to resize a stamp), but a real placement bug now that grip-drags can scale a stamp: moving a resized stamp would have placed it using its ORIGINAL size. Fixed to read through the current scale, matching the same pattern already used in `RegenerateBoundingBoxGizmo`/`BeginGripDrag`.
- **Undo**: sink depth is real per-actor state, not derivable from the transform alone, so `FIHStampUndoRecord` gained `PreviousDepthBelowSurfaceCm`, snapshotted at every Transform/Delete push site (Move, Rotate, Grip-drag, Delete) and restored alongside the transform in `UndoLastStampAction` - a no-op for actions that don't touch depth, but keeps Move-drag's own undo fully correct.
- **IH canon validation, as the user explicitly requested**: confirmed this is a DELIBERATE departure from IslandMesh's own relocation convention (Shift+Drag on an Island is X/Y only - islands don't have an adjustable Z, they sit at whatever height the terrain naturally is) rather than an inconsistency - the user's own framing ("Z added to Stamp Mesh Actor UNLIKE IslandMesh relocation where Z is NOT an option") already anticipates and accepts this asymmetry, since a placed landform (unlike a whole island) has a legitimate reason to want manual depth control. Shift+Wheel = rotate is unchanged from Stage 12a and remains consistent with the canonical `IslandShiftWheelRotateDeg` convention.
- **`IH_WB_Demo004Editor` builds clean.** Not yet PIE-visually-confirmed - needs the user's own pass (drag straight down while Shift+Dragging a selected stamp should visibly sink it into IslandMesh, stopping once ~50cm of its top remains above the surface; dragging back up should raise it, but never past the original ~1m-under-surface baseline).

### Stage 12c addendum (2026-09-11): three real bugs found on the second PIE pass

- **Double-click-to-reselect was silently broken by dilated game time, not by anything stamp-specific.** `TryHandleStampSelectionClickAtViewport`'s (and, it turns out, the pre-existing Island equivalent's) double-click window compared `World->GetTimeSeconds()` timestamps - DILATED game time. This project's own dev "Game Speed" slider (screenshotted at 7.5x) shrinks a real half-second double-click into ~0.06s of game time, making the 0.45s window physically unhittable by a human whenever speed isn't 1.0x - which, per every screenshot this whole session, it never has been. Root-caused directly from the log: consecutive real clicks 0.184s apart (well inside the window) still logged `dblClick=0` every time. Fixed both the stamp and Island double-click windows to use `GetRealTimeSeconds()` instead - a double-click is fundamentally a real-world human-input timing, not a simulation-time one.
- **Grip pin-compensation had a real math bug making Ctrl have no effect** ("grips should only extend in direction of pull unless Ctrl+"): `UpdateGripDrag`'s pin-opposite-face compensation re-transformed a LOCAL offset that was captured once in `BeginGripDrag` using the drag-START extent, comparing it against the actor's live transform each tick - but since that fixed local offset never reflected the mesh's newly-GROWN extent, the "current pin position" it computed was mathematically identical to the drag-start target every single tick, so the compensating location-shift was always exactly zero. Every grip-drag was silently behaving as if it were symmetric, regardless of Ctrl. Fixed by recomputing the pin point fresh from the mesh's just-applied new scale every tick, instead of reusing the stale drag-start value - only the FIXED WORLD target (captured once, correctly) still comes from `BeginGripDrag`.
- **Shift+Drag move reported as sluggish/jerky - sink depth redesigned to remove a likely noise-amplification source.** The first sink-depth implementation accumulated `CurrentDepthBelowSurfaceCm` incrementally from each tick's raw per-frame mouse delta - any tiny per-frame jitter (sub-pixel cursor noise, frame-timing irregularity) would compound over time rather than cancel out. Redesigned to match every other grip's own proven pattern: `SetManualSinkDepthFromDragTotal` re-derives depth fresh each tick from the drag's starting depth plus the TOTAL vertical cursor distance moved since mouse-down (`ViewportCur.Y - LeftMouseDragStart.Y`), never accumulating - immune to per-frame noise by construction, and exactly reversible (mouse back at its start Y always means exactly the starting depth, no drift). Not confirmed as the sole cause of the reported jerkiness, but a clear correctness improvement either way.
- **`IH_WB_Demo004Editor` builds clean.** None of these three fixes are PIE-confirmed yet.
